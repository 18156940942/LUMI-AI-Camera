# 05 · 单元测试说明

> 本文档说明 LUMI AI Camera 的测试套件：**每个文件在守什么规则、这些期望值是怎么算出来的、怎么在本地跑、以及测试覆盖不到什么。**

---

## 一、先说清楚这份测试的定位

这个项目的开发环境是 **Windows**，没有 Xcode，也没有 `swiftc`。所以测试套件在设计上刻意遵循一条原则：

> **只测「能用数字断言」的东西，不写「跑通即可」的测试。**

原因很直接：我没有编译器可以在写代码时反复验证，所以测试承担了两份额外职责：

1. **替我当编译器** —— 全部测试都用 `@testable import LUMI`，会对被测类型做真实引用。如果某个类型名、属性名、方法签名不存在，**测试文件本身就会编译失败**。这是在没有 Xcode 的情况下唯一能做的「符号级」检查（Windows 侧的 `scripts/check_symbols.py` 也做同一件事，但那是正则近似，测试是真正的类型检查）。
2. **替我当验收人** —— 每条期望值都是手算的常量。测试失败时能直接从坐标推出正确答案，而不是「再跑一次看看」。

### 测试能保证什么

- 几何方向约定没有被搞反（Vision 原点左下 ↔ SwiftUI 原点左上）；
- 所有阈值边界（2% / 5% / 35% 头顶留白、3° / 8° 肩线、15° 偏航……）能被精确命中；
- **门控行为**：没检测到人就绝不给结论、置信度不足就绝不给角度；
- 姿势库数据库的完整性（32 条、12 场景 7 风格全覆盖、角度在人体可执行范围内）；
- 文案与参数的一致性（参数写 30°，文案里就必须是 30°）。

## 二、怎么跑

### 方式 A：GitHub Actions（没有 Mac 就走这条）

不需要任何本地环境。推送代码后自动触发：

```bash
git add -A
git commit -m "run tests"
git push origin main
```

流水线里的 `preflight` job 在 ubuntu 上跑静态校验，`build` job 在 `macos-15` 上跑：

```bash
# 自动挑选可用的 iOS 模拟器（脚本内部按 iOS 版本 + 机型代数排序，不会误选 iPhone SE）
UDID=$(python3 scripts/pick_simulator.py)

xcodebuild test \
  -project LUMI.xcodeproj \
  -scheme LUMI \
  -destination "id=$UDID" \
  CODE_SIGNING_ALLOWED=NO CODE_SIGN_IDENTITY="" \
  PROVISIONING_PROFILE_SPECIFIER="" DEVELOPMENT_TEAM=""
```

测试结果会汇总到 Actions 页面的 Summary 里（用 `xcresulttool get test-results summary` 提取）。**测试失败则不会生成 ipa。**

### 方式 B：本地 macOS

如果你有 Mac（或者借到一台）：

```bash
# 1. 先确认工程文件是最新的（新增/删除 .swift 后必须跑）
python3 scripts/generate_xcodeproj.py
python3 scripts/validate_project.py

# 2. 列出可用模拟器，挑一个 iOS 17+ 的
xcrun simctl list devices available

# 3. 跑测试
xcodebuild test \
  -project LUMI.xcodeproj \
  -scheme LUMI \
  -destination 'platform=iOS Simulator,name=iPhone 15 Pro'

# 或者只跑某几个类
xcodebuild test -project LUMI.xcodeproj -scheme LUMI \
  -destination 'platform=iOS Simulator,name=iPhone 15 Pro' \
  -only-testing:LUMITests/PoseGeometryTests \
  -only-testing:LUMITests/PoseCoachEngineTests
```

在 Xcode 里打开则直接 `⌘U`。测试导航器里能看到全部 252 个测试方法。

### 方式 C：Windows 上的静态预检（能跑的替代品）

虽然跑不了 XCTest，但可以在 Windows 上跑一套静态检查，抓的是「数据与代码不一致」这类错误：

```bash
python scripts/preflight.py
```

它会依次做四件事：

1. **姿势库 ↔ Swift 枚举交叉校验** —— 解析 `pose_library.json` 里的每个枚举字段，去 `LUMI/Models/PoseTypes.swift` 里核对这个 case 是否真的存在；同时校验角度范围（`bodyRotation` 允许 0–180°，其他旋转字段 0–90°）、`direction == "none"` ⇔ `degrees == 0`；
2. **重新生成 Xcode 工程**；
3. **校验工程结构** —— UUID 引用完整性、Sources 阶段是否覆盖磁盘上每个 `.swift`、Resources 阶段是否包含资源；
4. **源码交叉引用检查** —— 扫描测试与主源码里出现的类型名，报告「引用了但项目里没定义」的可疑符号。

**这套预检是有效的，不是摆设**：它实际抓出了 4 处旋转角度阈值错误（`outdoor-04` 120°、`side-01` 95°、`back-01` 130°、`back-02` 165° 被错误地判为越界——数据是对的，是我的校验阈值写错了）、1 处文案缺陷，以及 2 个脚本自身的 bug。在 CI 迭代期间它又扩到了 8 项，新增的 `openseplist.py`（OpenStep 文法解析）、`check_conformance.py`（Hashable 合成 / init 完整性）与孤儿对象检测，分别精确定位了后面几轮 CI 的真实编译错误。

它通过后的输出长这样：

```
全部 8 项通过。可以推送到 GitHub 触发云端 macOS 构建了。
```

## 三、测试夹具：手算值是怎么来的

全部几何测试都建立在 `LUMITests/TestFixtures.swift` 上。这个文件没有测试方法（0 个），它是**所有其他测试的地基**。

### 3.1 标准站姿的 19 个关键点

坐标是 `Fixtures.standardStanding`，用的是 **Vision 归一化坐标系：原点在画面左下角，y 轴向上**。这一点非常重要——它和 SwiftUI 绘制坐标系（原点左上、y 向下）是**垂直翻转**的关系。搞混了 UI 上会「有数字但方向全反」，肉眼极难发现，所以有专门的测试守着。

坐标设计成了一个**故意保持对称与居中**的人工姿态：

| 部位 | 坐标 | 设计意图 |
|---|---|---|
| `nose` | (0.500, 0.880) | 正好在画面水平中线，且正好在双耳中点 → 头部偏航 = 0° |
| `leftEye` / `rightEye` | (0.483 / 0.517, 0.896) | 等高 → 头部歪斜 = 0° |
| `leftEar` / `rightEar` | (0.466 / 0.534, 0.884) | 关于 0.5 对称 |
| `leftShoulder` / `rightShoulder` | (0.400 / 0.600, 0.800) | 等高 → 肩线倾斜 = 0° |
| `leftHip` / `rightHip` | (0.440 / 0.560, 0.600) | 等高 → 髋线倾斜 = 0°，且 x 中点 = 0.5 → 躯干倾斜 = 0° |
| `leftAnkle` / `rightAnkle` | (0.440 / 0.560, 0.100) | 画到画面底部 |
| `leftWrist` | (0.410, 0.620) | y = 0.620 落在髋部高度带内 |
| `rightWrist` | (0.580, 0.580) | 也落在髋部高度带内 |

由这组坐标**手工推导出的期望值**（写在文件头注释里，供各测试引用）：

- **包围框** = x ∈ [0.370, 0.630]，y ∈ [0.100, 0.896]
  → 中心 x = 0.500（因为左右肘是最外侧点，0.370 与 0.630 对称）
  → 头顶留白 = 1 − 0.896 = **0.104 = 10.4%**（落在「可接受」区间 5%–35% 内）
- **肩线倾斜** = 0°、**髋线倾斜** = 0°、**躯干倾斜** = 0°、**头部歪斜** = 0°
- **头部偏航** = 0°（鼻尖 (0.500) 恰好等于双耳中点 (0.466+0.534)/2 = 0.500）
- **综合置信度** = 0.85，每个关节置信度 = 0.9
- **左肘角 ≈ 132.3°**：以左肘 (0.370, 0.680) 为顶点，指向左肩 (0.400, 0.800) 与左腕 (0.410, 0.620)
  → 向量₁ = (0.030, 0.120)，向量₂ = (0.040, −0.060)
  → cos θ = (0.030×0.040 + 0.120×(−0.060)) / (√0.0153 × √0.0052) ≈ −0.006 / (0.12369 × 0.07211) ≈ −0.6727
  → θ ≈ **132.3°**
- **右肘角 ≈ 139.4°**：同理，以右肘 (0.630, 0.680) 为顶点
  → θ ≈ **139.4°**
  两者都落在「弯曲自然」区间（55° < θ < 168°）内，**不应该触发任何肘部告警**
- **左右手腕都在髋部高度** → 会触发 `pose-wrist-low` 这条**启发式**（注意是 `heuristic` 而不是 `objective`）提示

这些数值的一个好处是：**它们让「正常姿态 → 零告警」成为一个可断言的基线**。任何把阈值改坏的改动都会立刻让基线测试失败。

### 3.2 `PoseBuilder`：链式修改器

如果每个测试都手写一份 19 点字典，那会又臭又长还容易写错。所以夹具提供了一个链式构造器，**每次修改都返回新实例**（避免测试之间互相污染）：

```swift
// 「右肩下移 10°」这个场景
let pose = Fixtures.PoseBuilder()
    .moving(.rightShoulder, to: CGPoint(x: 0.600, y: 0.770))
    .build()
```

可用的方法：

| 方法 | 用途 |
|---|---|
| `moving(_:to:)` | 平移某个关节（模拟姿态变化） |
| `removing(_:)` / `removing(_:)`（数组） | 删掉某个关节（模拟「该关节没检测到」） |
| `withConfidence(_:_:)` | 单独设置某关节置信度（模拟低质量检测） |
| `withDefaultConfidence(_:)` | 设置全部关节的默认置信度 |
| `withOverallConfidence(_:)` | 设置综合置信度（用于测试门控） |
| `keepingOnly(_:)` | 只保留给定关节（用于构造「只有上半身可见」） |
| `build(timestamp:)` | 生成 `BodyPose`，自动统计有效关节数 |

`build()` 里会自动算 `detectedJointCount` = 置信度 ≥ `BodyPose.defaultThreshold`（0.25）的关节数。这一点很关键：门控测试里「有效关节数不足」这条分支靠的就是它。

### 3.3 图像夹具

`ImageQualityCalculatorTests` 需要真实像素。三个函数：

- **`solidGrayImage(value:size:)`** —— 用 `CGContext` 画一张纯色灰度图。数据由 `CGContext` 自己分配，生命周期安全（不是 `malloc` 后裸传）。
  期望值：**方差 = 0、边缘密度 = 0、拉普拉斯方差 = 0**。
- **`checkerboardImage(size:block:)`** —— 黑白棋盘格。相邻像素差异极大。
  期望值：**边缘密度与清晰度评分都显著高于纯色图**（这是「清晰度指标真的在工作」的反向验证——如果纯色图和高频图得到一样的分，说明指标根本没读像素）。
- **`grayBuffer(pixels:width:height:)`** —— 手写灰度缓冲，完全可控。
  用来精确断言 `mean` / `stddev` / 边缘密度，不受 `CGContext` 行为影响。

为什么要有「纯色图方差必须为 0」这么极端的断言？因为这是唯一能证明**指标真的在计算像素**、而不是返回了一个「看起来挺合理」的默认值的方法。如果某天有人把 `metrics(from:)` 改成返回缓存值或者常量，这条测试会立刻炸。

### 3.4 `makePoseSuggestion(...)`

构造一条用于推荐的 `PoseSuggestion`。默认值刻意做得**中性且完整**（`id: "test-01"`、`scenes: [.outdoorPortrait]`、`styles: [.naturalRelaxed]`、`shotType: .halfBody`……），各测试只覆盖自己关心的那一两个字段，避免测试之间的隐性耦合。

### 4.1 `PoseGeometryTests.swift`（28）—— 锁死方向约定

> 守的是：**坐标系方向不能被搞反。**

这是整个项目里最容易出隐性 bug 的地方。Vision 用归一化坐标、原点左下、y 向上；SwiftUI `Canvas` 用原点左上、y 向下。搞反了不会崩、不会报错，只会让所有「向左/向右」的文案整体反掉。

关键用例：

- `testLineAngleHorizontalIsZero` / `testLineAngleVerticalIsPositiveNinety` —— 后者明确验证「第二个点更高 ⇒ +90°」，这是 Vision 约定的直接体现；
- `testTiltIsNormalizedIntoMinus90To90` —— 倾斜角必须归一化：肩线没有方向性，135° 和 −45° 是同一条线；
- `testAngleDegreesHandlesDegenerateInput` —— 重复点不能抛异常也不能返回 NaN（真实检测里重复点很常见）；
- `testTorsoLeanIsPositiveWhenShouldersShiftToScreenRight` —— 肩相对髋偏向**画面右侧**时必须是**正**角度；
- `testDirectionTextUsesScreenReference` —— 方向文案必须用「画面左侧/右侧」这种摄影师能理解的参考系，不能用坐标符号；
- `testDirectionTextFallsBackWhenPointsCoincide` —— 两点重合时返回「与参考点大致重合」，而不是「向右 0°」这种误导性文案；
- `testFlippedPointInvertsY` / `testFlippedRectInvertsYUsingMaxY` —— 翻转函数（矩形要用 `maxY`，不是简单的 `1 − y`）；
- `testWristZoneBands` —— 手腕高度分带的边界；
- `testHeadYawIsZeroWhenNoseIsCenteredBetweenEars` / `testHeadYawIsPositiveWhenNoseShiftsToScreenRight` —— 偏航估算；
- `testHeadYawFallsBackToEyesWhenEarsMissing` —— 耳朵不可用时要退回用眼睛（且置信度要打折）；
- `testHeadYawReturnsNilWithoutNose` —— 连鼻子都没有就必须返回 nil，**不能猜**；
- `testHeadRollIsPositiveWhenScreenRightEyeIsHigher` —— 歪头方向；
- `testHeadroomIsDistanceFromBoxTopToFrameTop`、`testLeadRoomFollowsGazeDirection`、`testDeviationFromNearestThird`、`testHorizontalOffsetAndSubjectHeightRatio` —— 构图几何的四个基础量。

### 4.2 `BodyPoseTests.swift`（14）—— 「没有检测到人」必须是空的

> 守的是：**只有真实检测到的关键点才进入数据流，绝不用占位值把结构填满。**

- `testEmptyPoseHasNoPointsAndNoBoundingBox` —— `.empty` 必须是真的空，不能有一个「默认包围框」；
- `testStandardFixtureHasAllNineteenJoints` —— 夹具本身要完整；
- `testPointRespectsConfidenceThreshold` —— 低于阈值的关键点必须被 `point(_:)` 拒绝，防止低质量坐标进入几何计算；
- `testValidJointCountExcludesLowConfidenceJoints` —— 计数要把低置信度排除掉；
- `testBoundingBoxMatchesJointExtremes` / `testBoundingBoxIgnoresLowConfidenceJoints` —— 包围框由坐标极值算出，且不吃低置信度点；
- `testMidpointReturnsNilWhenEitherJointIsUnreliable` —— 中点缺少任一端点就必须 nil；
- `testTruncatedSidesDetectsTopTruncation` / `…BottomTruncation` / `testTruncatedSidesIsEmptyForWellFramedSubject` —— 出画检测；
- `testSkeletonEdgesReferenceExistingJoints` —— 骨架连线不能引用不存在的关节（这是个真实的连线图 bug 来源）；
- `testEveryJointHasDisplayNameAndVisionName` / `testUpperAndLowerBodyJointGroupsAreDisjointAndNonEmpty` —— 枚举完整性。

### 4.3 `PoseAnalyzerTests.swift`（13）—— 每个数字都能由坐标反推

> 守的是：**报告里的每个角度都对应真实坐标，不存在随机值或占位值。**

- `testEmptyPoseProducesEmptyReport` —— 没人物就没报告；
- `testShoulderTiltMatchesCoordinates` —— 右肩下移使倾斜角为 −10°，且**符号要与「画面右侧肩膀更低」一致**；
- `testShoulderTiltUsesScreenOrderNotVisionNaming` —— 这条很重要：左右描述必须按**画面左右**排序，不能直接用 Vision 给的 `left` / `right` 命名（正面人像里两者是相反的）；
- `testHipTiltMatchesCoordinates` / `testTorsoLeanMatchesCoordinates` —— 同样跟着坐标走；
- `testPersonCenterOffsetFollowsBoundingBox`、`testReachingFrameEdgeIsTrueWhenSubjectIsTruncated`；
- `testWristZoneTextIsPopulatedForBothHands`；
- `testAngleFindingsEmbedMeasuredNumbers` —— **每条角度结论里都必须出现实测数值**（让摄影师能自己复核，而不是只能相信 App）；
- `testReliabilityFollowsConfidence` —— 可靠性等级跟随置信度；
- `testThreeQuarterViewHeadTurnIsReflectedInReport` —— 四分之三侧脸要被识别出来。

### 4.4 `PoseCoachEngineTests.swift`（23）—— 三条底线

> 守的是：① 置信度/关键点不足时**必须闭嘴**；② 每条建议都要带实测数值；③ 阈值边界能精确命中。

**门控（最重要的一组）**：

- `testNoPersonProducesSingleExplicitFinding` —— 没人物时只输出**一条**明确的 `pose-none`，不给角度；
- `testLowConfidenceSuppressesEveryAngleConclusion` —— 置信度 < 0.30 时，**任何角度结论都不允许出现**，只说明「识别不稳定」并列出不可靠关节；
- `testInsufficientValidJointsSuppressesConclusions` —— 有效关节 < 8 时同样闭嘴；
- `testGateBoundaryIsInclusive` —— 门控用严格小于（`<`），正好等于阈值时要放行，保证阈值语义清晰、不留模糊地带。

**边界数组**（每一组都同时测「刚好触发」和「刚好不触发」）：

| 指标 | 阈值 | 用例 |
|---|---|---|
| 肩线倾斜 | 3° / 8° | `testShoulderTiltIsGoodWhenLevel`、`…AttentionAboveThreeDegrees`、`…WarningAboveEightDegrees` |
| 躯干倾斜 | 4° | `testNoTorsoLeanFindingWhenUpright`、`testTorsoLeanAttentionWhenAboveFourDegrees` |
| 头部偏航 | 15° | `testNoHeadYawFindingWhenFacingCamera`、`testHeadYawIsReportedAsEstimateWhenExceedingFifteenDegrees` |
| 头部歪斜 | 6° | `testHeadRollIsReportedWhenExceedingSixDegrees` |
| 肘部 | 55° / 168° | `testElbowTooStraightIsFlagged`、`testElbowTooClosedIsFlagged`、`testNaturalElbowBendIsReportedAsGood` |
| 人物居中偏移 | 0.10 / 0.22 | `testCenterOffsetIsSilentWhenCentered`、`…InfoWhenSlightlyOff`、`…AttentionWhenFarOffCenter` |

**启发式 vs 客观**：

- `testBothWristsLowProducesHeuristicSuggestion` —— 「双手都偏低」只能是 `heuristic`（这是审美偏好，不是客观错误）；
- `testUnevenWristHeightsProducesNoWarning` —— 高度不一致时不应该乱告警；
- `testTorsoScaleIsAlwaysReportedAsHeuristic` —— 人物在画面里的大小建议也永远是启发式。

**输出质量**：

- `testAllFindingsHaveUniqueKeysAndNonEmptyText` —— 所有 finding 的 key 必须唯一、文案非空。这条防止 UI 列表出现重复项或空行。

肘部的 key 带左右区分（`pose-elbow-straight-左臂` / `-右臂`），所以同一条规则可以同时给两只手各出一条建议而 key 不冲突。

### 4.5 `CompositionAnalyzerTests.swift`（24）—— 没有人物就没有结论

> 守的是：① **没有人物就绝不编出一份构图报告**；② 每条结论都标注是「实测」还是「建议」；③ 阈值边界能精确命中。

**无人门控**：

- `testNoSubjectProducesNoCompositionConclusion` —— 只返回一条 `composition-no-subject`；
- `testNoSubjectDetectionSourceIsExplicit` —— 来源字段必须显式说明「未检测到人物」，而不是留空让人误以为「分析过了但没问题」。

**头顶留白（4 档）**：阈值 2% / 5% / 35%

- `testHeadroomTightBelowTwoPercent` → warning（头顶快贴边了）
- `testHeadroomAttentionBetweenTwoAndFivePercent` → attention
- `testHeadroomGoodInNormalRange` → good
- `testHeadroomExcessiveAboveThirtyFivePercent` → attention（头顶留白过多 → 人物在画面里太小）

**视线留白**：

- `testLeadRoomIsSkippedWhenSubjectFacesCamera` —— 人正对镜头时**不谈**视线留白（因为不存在视线方向）；
- `testLeadRoomAttentionWhenGazeSideIsCramped` —— 视线方向那侧太挤时提示。

**三分法**：

- `testThirdsReportedAsInfoWhenSubjectIsCentered` —— 居中时只是 info，不是错误（居中构图完全合法）；
- `testThirdsRecognizedWhenSubjectCenterSitsOnThirdLine`；
- `testThirdsDeviationMatchesMeasurement` —— 偏差数值必须与实际测量一致（容差 0.045）。

**截断**：

- `testTruncationProducesWarning`；
- `testTruncationMentionsJointOnEdgeWhenCutAtJoint` —— 切在关节处时要**说出是哪个关节**（「膝盖被切」比「人物被截断」有用得多）。

**景别推断**：

- `testShotTypeIsFullBodyWhenLegsAreVisible`；
- `testShotTypeIsSeatedWhenKneeAngleIsSharp`；
- `testShotTypeIsHalfBodyWhenLegsAreNotVisible`；
- `testShotTypeIsCloseUpWhenOnlyUpperBodyIsReliable` —— 腿都不可靠时不能硬说全身。

**背景干扰**：

- `testBackgroundNotEvaluatedWhenNoClutterValueProvided` —— **没算就直说没算**，不能给个默认「背景干净」；
- `testBackgroundAttentionWhenClutterIsHigh` / `testBackgroundGoodWhenClutterIsLow`（阈值 0.42）。

**性质标注**：

- `testEveryFindingCarriesKindLevelAndDetail`；
- `testObjectiveAndHeuristicFindingsAreSeparable` —— `objectiveFindings` / `heuristicFindings` 两个数组要能把两类完全分开，UI 上「实测」/「建议」的徽章就靠这个。

### 4.6 `ImageQualityCalculatorTests.swift`（20）—— 指标真的在算像素

> 守的是：① 纯色图方差/边缘密度必须是 **0**；② 高频图清晰度必须显著更高；③ 归一化必须钳制在 0…1。

- `testMetricsOnHandwrittenBuffer` —— 用手写缓冲断言 `mean` / `stddev` 的精确值；

- `testSharpnessLabelThresholds` / `testExposureLabelThresholds` —— 文案档位边界；
- `testEdgeDensityOnSolidRegionIsZero`、`testExcludingRegionReducesSampleCount`（背景密度要**排除**人物区域）、`testBackgroundEdgeDensityIsNilWithoutSubjectBox`（没给人物框就必须 nil）、`testBackgroundEdgeDensityIsComputedWithSubjectBox`、`testDegenerateRegionReturnsZeroInsteadOfCrashing`；

### 4.7 `ExifReaderTests.swift`（12）—— 读不到就是 nil

> 守的是：**文件里有什么就读什么，读不到就返回 nil，绝不编造。**

- `testApertureAndShutterFormatting`（f/1.8、1/200s）、`testFocalTextShowsEquivalentWhenDifferent`（35mm 等效焦距与实际不同才显示）、`testMegapixelTextFormatting`；

### 4.8 `PhotoAnalyzerTests.swift`（14）—— 真实结果而非合理默认值

> 守的是：**拿到的是真实计算结果，不是一堆看起来合理的默认值。**

用真实 JPEG 走完整链路（EXIF → Vision → 像素指标 → 汇总）：

- `testGarbageDataReturnsNil` / `testEmptyDataReturnsNil` —— 输入保护；
- `testAnalyzeProducesMeasuredResultForRealPhoto` —— 真实照片要产出实测结果；

- `testSummaryAlwaysProvidesAtLeastOneSuggestion` —— 建议列表不能为空（哪怕照片很好也要有正面反馈）；
- `testOverallScoreIsClampedToValidRange`；
- `testAnalyzedAtTimestampIsRecorded`、`testSharpnessLabelMatchesScore`、`testSharpnessLevelMapping`；

### 4.9 `PoseRecommenderTests.swift`（17）—— 不联网也能用

> 守的是：**同一组输入永远得到同一个排序；每条推荐都能说清楚为什么。**

权重是显式的：`sceneMatch = 5`、`styleMatch = 4`、`shotTypeMatch = 3`、`scenePreferredShotType = 2`、`difficultyPenaltyPerLevel = 3`。

- `testExactMatchOutranksMismatch`、`testMultipleSceneHitsAccumulate`、`testStyleMismatchPenaltyIsHalfOfStyleWeight`、`testScenePreferredShotTypeBonusWhenShotTypeNotSpecified`；
- `testDifficultyPenaltyForHardPosesBeyondLimit` / `testNoPenaltyWhenDifficultyWithinLimit` / `testEasyPoseGetsExplainedInReasons`；
- **排序稳定性**：`testTieIsBrokenByLowerDifficultyFirst`、`testTieIsBrokenByIdWhenScoreAndDifficultyMatch`、`testRecommendationIsDeterministicAcrossRepeatedCalls`；
- `testSceneMismatchNeverEmptiesTheResultSet` —— **场景不匹配只能降权，绝不能把结果清空**（否则用户选了一个没有对应姿势的场景就会看到空白列表）；
- `testEmptyQueryReturnsAllPoses`、`testLimitIsRespected`、`testResultNeverExceedsInputSize`、`testEmptyInputProducesEmptyResult`；
- `testReasonsExplainSceneStyleAndShotTypeMatches`、`testScoreIsSumOfDocumentedWeights` —— 分数必须等于文档化权重之和（防止有人偷改权重导致推荐质量静默下降）。

### 4.10 `PoseScriptWriterTests.swift`（22）—— 文案与参数永不矛盾

> 守的是：**输出必须是具体可执行的指令，且文字里的角度必须由参数生成。**

这是「姿势助手真的能用」的关键。如果文案是手写的，就会出现「参数写 30°、文案写 45°」这种自相矛盾；如果文案是形容词（「放松一点」），那这个功能就等于没有。

- `testBodyTextEmbedsRotationDegreesAndDirectionFromParameters` —— 文案里的角度必须来自参数；
- `testBodyTextChangesWithParametersToStayConsistent` —— 改参数，文案必须跟着变；
- `testBodyTextForFacingPoseDoesNotMentionRotation` —— 正对镜头时不谈旋转；
- `testHeadTextCombinesTurnAndChinCue`、`testHeadTextForFacingHead`；
- `testHandsTextNumbersBothHandsWhenTheyDiffer` —— 左右手不同时用 ①② 编号；`testHandsTextIsSingleWhenOnlyOneHandIsSpecified` / `…BothHandsAreTheSame`；
- `testCompositionTextReflectsHorizontalAnchor`、`…IncludesHeadroomPercentage`、`…MentionsLeadRoomOnlyWhenNeeded`、`…AppendsNoteWhenPresent`；
- `testStepsCoverAllMajorCategories` —— 11 个步骤分类都要出；
- `testStepsSkipEnvironmentAndTipsWhenEmpty` —— 没内容就不要硬凑空步骤；
- `testStepIdentifiersAreUniqueAndStable`、`testEveryStepHasNonEmptyTextAndTitle`、`testEveryStepCategoryIsCoveredByAllCases`；
- `testShortDigestContainsShotTypeAndGaze`、`testShortDigestOmitsRotationForFacingPose`；
- `testAllPoseEnumsHaveExecutableText` —— 遍历全部枚举 case（9 种下巴示意、7 种视线锚点、6 种肩部提示、16 种手部位置、5 种重心、9 种腿部、7 种机位角度），确保每个都有可执行文案；
- **`testLargeRotationUsesBackToCameraWording`** —— 大角度必须换成「背对」这种可立即执行的说法。这条是预检脚本抓出的真实缺陷：原始实现会说「旋转 165°」，但 165° 需要在脑子里换算，而「背对镜头」不用。修正后超过 135° 会输出「近乎背对镜头（向左侧转约 165°）」——**既给了可执行的说法，也保留了精确数值**。

### 4.11 `PoseLibraryDatabaseTests.swift`（23）—— 数据库体检 + 打包配置检查

> 守的是：**姿势库数据完整、合法，并且真的被打进了 App 包。**

这些测试直接读取**随 App 一起打包的** `pose_library.json`（宿主包优先，测试包兜底）。所以它们同时是一份**构建配置检查**：一旦这个文件哪天被移出 Copy Bundle Resources，测试会立刻失败——而不是等到用户打开「姿势助手」看到空列表才发现。

- `testDatabaseFileExistsAndDecodesIntoSuggestionModels` —— 能解码成 `PoseSuggestion` 模型；
- `testDatabaseContainsExpectedNumberOfPoses`（32 条）、`testAllIdentifiersAreUnique`；
- **覆盖度**：`testAllTwelveScenesAreCovered`（12 个场景）、`testAllSevenStylesAreCovered`（7 种风格）、`testAvailableScenesAndStylesReflectDatabase`；
- `testEveryPoseHasCompleteAndUsableContent` —— 名称/摘要/环境/关键词/提示都不为空；
- `testCompositionParametersAreInRange` —— 头顶留白比例在 0.10–0.50；
- **`testRotationParametersAreSane`** —— 这条是被预检脚本「反向修好」的：最初我写的上限是 90°，但 `bodyRotation` 表示身体相对镜头转多少，**回头和背身本来就需要 > 90°**（165° 是合理的）。真正需要检查的不是「≤ 90°」，而是「`direction == none` ⇔ `degrees == 0`」以及「角度 ≤ 180°」。限制改成按字段区分：`bodyRotation ≤ 180`，其他旋转字段 ≤ 90°；
- `testEveryPoseProducesCompleteExecutableSteps` —— 每条姿势都能生成完整分步；
- `testBodyAndHeadInstructionsAreSpecific` —— 身体朝向与头部指令里**必须出现角度或方向词**，否则就退化成「放松一点」这种没用的建议了；
- `testHandInstructionsAreSpecific`；
- 推荐与检索：`testRecommendationWorksWithEmptyQuery`、`testRecommendationReturnsDescendingScores`、`testRecommendationExplainsSceneMatch`、`testSceneFilteringNeverReturnsEmpty`；
- `testSearchMatchesChineseKeywords`、`testEmptySearchReturnsEverything`、`testSearchReturnsEmptyForUnknownKeyword`、`testSearchMatchesSceneTitles`、`testSearchByNameReturnsThatPose`、`testPoseLookupByIdentifier`、`testPosesInSceneAndWithStyleAreConsistent`。

检索是「名称 + 摘要 + 环境 + 关键词 + 摄影提示 + 场景标题 + 风格标题」的并集，所以命中范围会大于场景标签本身——测试注释里写明了这一点，只断言它确实能命中，不做过强的断言。

### 4.12 `PoseTypesTests.swift`（12）—— 需求里写死的维度

### 4.13 `VideoInputModelsTests.swift`（30）—— 最重要的诚信规则

> 守的是：**不能假装 iPhone 能接 UVC 采集卡。**

这些看起来是「数据类」的测试，但它们守住的是整个项目最重要的一条诚信规则。一旦有人为了「让它看起来能用」而放宽判定，这些测试会立刻失败。

- `testStateLabelsAndRunningFlag`、`testDeviceInfoTextHelpers`、`testDeviceInfoShowsUnknownWhenSystemReportsNothing`（系统没报告就显示「未知」，不能编）、`testFourCharCodeConversion`（`'420f'` 这类四字符码转字符串，空白的要转成 nil）；

## 五、测试覆盖不到的部分（诚实说明）

| **`SettingsStore` / `FavoritesStore` / `PresetStore`** | 依赖 `UserDefaults` | 简单键值存取，风险较低 |
| **启动与生命周期**（`LUMIApp`、`OrientationAppDelegate`） | 需要真机 | — |

设计上的应对：**把所有能测的逻辑都从视图里挤了出来**。14 个 View 文件基本只做布局与绑定，真正的判断（阈值、门控、权重、几何、文案生成）全在 `Models` / `PoseEstimation` / `AIAnalysis` 里，这些都有测试。

另外，`LUMI/VideoInput/*.swift` 这 6 个文件是测试覆盖最薄的部分。如果你后续要在真机上调试，**优先怀疑这里**。

## 六、维护提示

### 改了姿势库数据之后

必跑 `python scripts/preflight.py`。它会校验：

- JSON 里的每个枚举字符串在 `PoseTypes.swift` 里真实存在；
- 角度范围合法；
- `direction == "none"` 与 `degrees == 0` 一致；
- Xcode 工程文件是最新的。

### 新增/删除了 `.swift` 文件之后

必跑：

```bash
python scripts/generate_xcodeproj.py    # 重新生成（UUID 是确定性的，不会产生 diff 噪音）
python scripts/validate_project.py      # 校验 Sources 阶段是否覆盖了磁盘上每个文件
```

忘了这一步的典型后果是「文件在磁盘上但没被编译」——测试也一起失败。

### 修改了阈值之后

阈值常量集中在两处，改的时候要同步改对应的测试：

- `PoseCoachEngine.Thresholds` —— 实时姿势指导的所有阈值；
- `CompositionAnalyzer.Thresholds` —— 构图分析的所有阈值。

测试里对每个阈值都同时测了「刚好触发」和「刚好不触发」两侧，所以改错方向会立刻失败。

### 新增测试时的约定

1. **不用随机数** —— 期望值必须是手算常量，失败时要能直接推出正确答案；
2. **同时测两侧边界** —— 只测「触发了」不测「没触发」，等于没测阈值；
3. **断言具体数值而不是「不为空」** —— `XCTAssertEqual(report.shoulderTiltDegrees, -10, accuracy: 0.01)` 比 `XCTAssertNotNil(report.shoulderTiltDegrees)` 有力得多；
4. **门控分支必须有测试** —— 任何「不给结论」的分支（无人物、低置信度、无 EXIF、没算背景）都要有一条测试守着，这是这个项目的诚信底线。
