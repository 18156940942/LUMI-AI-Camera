# 真机验收清单

本文档是**在 iPhone 上实机验证 LUMI** 的操作清单。每次重签（免费账号 7 天一次）后都可以照着重跑一遍。

> **为什么需要这份清单**：开发这套代码的机器是 Windows，没有 Mac。这意味着**没有 Xcode 控制台、没有 Instruments、没有 `log stream`** —— 所有「跑起来之后怎么样」的信息，只能靠手机上的画面和 App 内置的诊断页传出来。这份清单就是把「在手机上点几下」变成「能拿到可分析的信息」。

### 第 3 条是什么问题

不是按钮没响应，而是**按钮生效了但界面不刷新**：

```swift
final class AppState: ObservableObject {
    let settings: SettingsStore            // 普通 let，不是 @Published
}

struct RootView: View {
    @EnvironmentObject var app: AppState   // 只订阅了 AppState
    get: { !app.settings.hasAcknowledgedPrivacy }   // 却去读子 Store
}
```

点下去后 `settings.hasAcknowledgedPrivacy` **确实被改成了 `true`**，但发出变化通知的是
`SettingsStore.objectWillChange`，而 `RootView` 订阅的是 `AppState.objectWillChange`。
SwiftUI 只重算「订阅了变化对象」的视图，所以 `RootView.body` 从不重算、
那个 Binding 的 `get` 从不重读，全屏页就一直盖着。

**这类缺陷为什么必须靠静态检查兜住**：它能编译、能通过全部单元测试
（不涉及任何可断言的逻辑），只有真机点一下才会暴露 —— 而本项目恰恰没有 Mac，
改一次要等十几分钟云端构建。

修复时顺带查出同一模式的另外 3 处（都不崩溃，只是安静地显示错数据）：

- 首页「本机数据」区的姿势数 / 收藏数 / 照片副本数**不刷新**；
- 首页的输入方式与「实时指导」开关状态不刷新；
- **诊断报告里可能写进过期的姿势库版本与条目数** —— 这一条最要紧，因为它会让
  回传给我的现场信息不可信。

现在预检里多了一道 `scripts/check_observation.py`，专门扫这类问题。
它上线前先拿修复前的代码验证过：**25 处全部命中**。

- **AI 分析管线当时有没有在出结果？** 这是 App 内部的事。那一次构建走的是
  `.info` 级 os.Logger，而设备日志流**只转发 default 及以上级别** —— 所以
  App 自己的日志一条都没出现。**本仓库已修正这一点**（见第五节），需要重装

> **一个副作用值得记住**：隐私确认页那个观察链缺陷**只在真正的首次启动才会卡住**。
> 因为按钮点击其实成功写入了 `UserDefaults`，而重装同一个 Bundle ID 的 App 时
> iOS 会保留容器 —— 所以第二次启动就直接进主界面了。
> 要复现「首次启动」流程，必须先**删除 App** 再装。

**同一段日志里还抓到 1 个运行期 `<Fault>`：**

```
17:48:25 LUMI(Foundation) <Fault>: String(format:locale:arguments:):
         Provided argument types ["Swift.String", "Swift.String", "CoreGraphics.CGFloat"]
         (with inferred specifiers ["%@", "%@", "%lf"])
         do not match the format string's specifiers
```

参数类型与格式串**逐个对得上**（两个 `%@` 收两个字符串、`%.1f` 收一个 CGFloat），
唯一「不匹配」的是 `%@` 拿到的是 Swift `String`，而不是 Objective-C 对象。
触发点是 `PoseCoachEngine` 的肩线倾斜建议 —— 格式串正是
`"实测：%@肩膀比%@低 %.1f°…"`，参数正是 `(String, String, CGFloat)`。

全项目共 **13 处**同样的写法（肩线、躯干、头部旋转、视线留白、画面偏移等建议文案），
已统一改为显式桥接：新增 `LUMI/Services/FormatSupport.swift`，里面是
`String.formatObject`（`self as NSString`）。

**这一段需要你在屏幕上确认一下**（我没法看画面）：打开一张照片，
看「肩线明显倾斜 / 肩线略有倾斜」那条建议的正文 ——
- 如果是通顺的中文（如「实测：画面左侧肩膀比画面右侧低 3.2°。…」），说明这次
  `<Fault>` 只是校验器严格，输出本身是对的；
- 如果正文里出现 `%@`、或数字错位、或整句消失，那它就是真缺陷。

两种情况都请告诉我，我会按结论决定要不要进一步改写这几条文案。

## 四、阶段 3：网络中继（今天可以用电脑摄像头替身）

Z6 II 没连上，但**中继这条路本身可以先测通**。我已在你的电脑上用**电脑自带摄像头**把中继跑起来了：

```
源   ：电脑内置摄像头（Chicony），640×480 @ ~10fps
监听 ：0.0.0.0:8090
手机侧地址：http://172.20.10.8:8090/stream
状态页    ：http://172.20.10.8:8090
健康检查  ：http://172.20.10.8:8090/health
```

**前置条件（这一步需要你做，我没有管理员权限）**

Windows 防火墙当前把 WLAN 判为 **Public** 且没有 8090 规则，**手机会被挡住**。用**管理员** PowerShell 跑一次：

```powershell
New-NetFirewallRule -DisplayName "LUMI relay 8090" `
  -Description "LUMI 相机中继（仅允许本地子网访问 TCP 8090）" `
  -Direction Inbound -Protocol TCP -LocalPort 8090 `
  -RemoteAddress LocalSubnet -Action Allow -Profile Any
```

不想要了可以删：`Remove-NetFirewallRule -DisplayName "LUMI relay 8090"`

**验证步骤**

1. 先在**电脑浏览器**打开 `http://127.0.0.1:8090` —— 能看到电脑摄像头的画面，说明中继本身没问题
   （这一步我已经替你验过：`/snapshot` 返回 HTTP 200、`image/jpeg`、16,622 bytes、JPEG 头 `ffd8ff`）
2. 在**手机浏览器**打开 `http://172.20.10.8:8090/health`
   - 能看到 JSON → 网络通了，问题只可能在 App 里
   - 打不开 → 防火墙没放行（回到上面那条命令）
3. 进 LUMI → 实时监看 → 输入方式选 **网络中继** → 填 `http://172.20.10.8:8090/stream`
4. 应该看到电脑摄像头的画面

**关键区分**（App 的日志会记这两件事）：
- **「已连接」** = HTTP 握手成功
- **「首帧到达」** = 真的出图了

如果显示已连接但**黑屏**，请打开诊断页做一次**中继自检** —— 它会给出六种可定位结论之一（连不上 / 超时 / HTTP 错误 / 能连上但没画面 / 正常 / 取消）。

**网络拓扑**（已核实）：电脑连在**手机的个人热点**上（PC `172.20.10.8`，网关 `172.20.10.1` 即手机），所以手机能直接访问电脑。

## 五、阶段 4：把现场信息交出来（最重要的一步）

有两条路。**A 更好，因为它不需要你做任何额外操作。**

### 方法 A：USB 设备日志流（不需要 Mac，也不需要你导出任何东西）

这个项目是在**没有 Mac 的 Windows** 上开发的，而 `os_log` 的输出只有 macOS 的
「控制台」或 Xcode 能读 —— 听起来是个死结。但 iPhone 通过 USB 接在电脑上时，
可以用 `libimobiledevice` 直接读设备日志，**Windows 上就能跑**。

```bash
# 首次：取工具（约 4.3 MB，会校验 SHA-256）
python tools/lumi_device_log.py fetch-tools

python tools/lumi_device_log.py info                # 机型 / iOS 版本
python tools/lumi_device_log.py apps --filter lumi  # 手机上装的是哪一次构建
python tools/lumi_device_log.py battery             # 温度 / 电流 / 瞬时功率
python tools/lumi_device_log.py watch --minutes 5 --power   # 抓 5 分钟，同时采功耗
python tools/lumi_device_log.py report --out 现场报告.txt    # 一份可粘贴的报告
```

**能拿到什么**：

- 采集会话的起停、**实际帧率**（`FigCaptureFrameCounter ... fps 29.998`）
- 应用前后台切换、方向变化
- **相机权限是否被拒**（被拒时不会有任何帧）
- 卡死前兆（`HangTracer`）、内存被强杀（`JetsamEvent`）、温控降频（`thermalmonitord`）
- 电池温度、电流、瞬时功率
- 崩溃报告（`crash` 子命令）

**拿不到什么**（这一条必须说清）：

- **不能操作手机**：不能点按钮、不能授权、不能启动 App。
- **App 自己写的 `.info` 级日志原本不会出现**在设备日志流里 —— iOS 的 syslog
  中继只转发 `default` 及以上级别。代码里已经按这条改过
  （`DiagnosticsLog.emitToOSLog` 的 `.info` 分支改用 `logger.log(...)`），
  **所以要用改了之后的构建才能看到 App 内部日志**。
- 不能截图：`idevicescreenshot` 需要 developer disk image，本项目没有。

### 方法 B：App 内诊断页（不需要电脑）

1. 进 **诊断页**（监看页工具栏的按钮，或设置 → 「设备自检与诊断」）
2. 点 **复制到剪贴板**
3. 粘贴给我

报告里包含：运行环境（机型/系统/热状态/低电量模式/可用存储）、权限状态、视频输入实时参数与**实测**帧率、中继自检结果、内存日志（最近 400 条）。

**它不含任何影像内容**，也不上传，纯内存、不落盘。

> 如果连 App 都打不开或一开就崩，那就没有诊断报告可拿。这时请告诉我：**崩在哪个画面**、**是白屏还是闪退**。闪退的话两条路都能拿到崩溃日志：上面方法 A 的 `crash` 子命令，或者手机上 **设置 → 隐私与安全性 → 分析与改进 → 分析数据**，找以 `LUMI` 开头的 `LUMI-2026-10-12-xxxx.ips`。
