### 编译是怎么完成的

开发这套代码的机器是 **Windows**，没有 Xcode，也没有 Swift 编译器 —— 这个前提**没有变**。iOS App 只能在 macOS + Xcode 上编译，这是 Apple 工具链的硬限制，没有任何绕开的方式。

变的是：编译**已经在 GitHub Actions 的 macOS runner 上真实执行过了**，不再停留在「理论上应该能编过」。

- **首次全绿**（验证这套代码能编译）：[Actions run #38198820127](https://github.com/18156940942/LUMI-AI-Camera/actions/runs/38198820127) —— `macos-15` runner，Xcode 16.4，`xcodebuild test`（模拟器）+ `xcodebuild archive`（真机 arm64、未签名）全绿，耗时 11 分 17 秒，产出 `Payload/LUMI.app/LUMI`（1.71 MB）。
- **当前状态**（含「设备自检与诊断」模块）：[Actions run #38204726462](https://github.com/18156940942/LUMI-AI-Camera/actions/runs/38204726462) —— 同样全绿，耗时 13 分 23 秒，可执行文件增至 1.85 MB，单元测试 **288 / 288**。

### 第一版代码确实编不过 —— 这一轮总共修了 6 个真实缺陷

这不是「应该早就发现」的疏漏，而是这类「无本地编译器」开发方式不可避免的成本。但它也不是「无法收敛」的：从第 1 轮工程文件打不开，到第 6 轮全绿，**每一轮的报错都指向一个具体缺陷，没有一个是玄学**。

| 轮次 | CI 报错 | 真实缺陷（不是误报） | 修法 |
|---|---|---|---|
| 1 | `The project 'LUMI' is damaged and cannot be opened due to a parse error`（exit 1） | `scripts/generate_xcodeproj.py` 用 `split("\n", 1)` 去拆分两个 pbxproj 区块，导致 `PBXTargetDependency` 块的右花括号被截断、`PBXContainerItemProxy` 段以孤立属性开头 | 让函数返回两个**各自完整闭合**的区块 |
| 2 | 同上（exit 74） | 分组树在深度 1 处生成了一个空路径 group，输出 `path = ;` —— OpenStep plist 里**空值是语法错误** | 跳过空 parent；并在 `section_groups()` 里对空 group 直接抛错 |
| 3 | `type 'ShootingPreset' does not conform to protocol 'Hashable'`（exit 65） | `OverlayConfiguration` 没声明 `Hashable`，而 `ShootingPreset` 把它当存储属性 —— Swift 只在**所有**存储属性都可哈希时才合成协议 | 给 `OverlayConfiguration` 加 `Hashable` |
| 4 | `return from initializer without initializing all stored properties`（exit 65） | `SettingsStore.init` 漏了 3 个属性的赋值 | 补齐赋值 |
| 5 | `testCenterOffsetInfoWhenSlightlyOff` 失败：`("nil") is not equal to ("Optional(LUMI.FindingLevel.info)")` | **产品代码的浮点边界缺陷**：把夹具平移 +0.10 后 `0.09999999999999998 < 0.10`，代码把「恰好等于阈值」判成了「未达到」 | 加 `thresholdEpsilon` 容差，10 处阈值比较全部改为 `reaches()` / `within()` |
| 6 | —— | **全绿**：`** TEST SUCCEEDED **`，252 / 252 | —— |
| 7 | 未报错。**审查诊断页要显示的数据时发现** | `FrameAnalysisPipeline.publishDiagnostics()` 里 `analysisFPS` 的分母两个分支都取到 0，实际算成了「累计分析帧数 ÷ 开机时长」→ 恒为 **0.0**。界面上有个指标，数值一直是废数 | 改为按 0.5 秒窗口算滚动帧率，算法抽成纯函数 `Diagnostics.rollingRate(...)` 并补 4 个边界测试 |

**第 5 轮有一个判断需要说明**：我选择**改产品代码，而不是改测试的期望值**。因为测试里的数值（0.10 这个阈值边界）是对的，错的是产品代码；而且代码库里已经有一条测试 `testGateBoundaryIsInclusive` 明确写着「边界算作已达到」。改测试的期望值等于推翻这条既有约定。

**第 7 轮更值得记下来**：它是**测试完全抓不到**的一类缺陷 —— 不崩溃、不抛异常、不断言失败，只是算出了一个合法但无意义的数。发现它的方式是「写一个页面去显示这个数，然后对着它问：这个数在真实环境里会是多少？」如果这个指标从来没被显示出来，它可能永远烂在那里。这也是我加「设备自检与诊断」模块的附带收益之一。

### 为了降低这个风险做了什么（以及实际抓到了什么）

1. **静态预检脚本 `scripts/preflight.py`**（**9 项**检查，Windows 上就能跑）。真实收获：
   - 抓出 4 条姿势的身体旋转角度是 95°–165°，而我最初的校验阈值写的是 0–90° —— 数据是对的（背身回望确实要转 165°），错的是阈值；同时顺带发现 `PoseRotation.descriptiveText` 在大角度下会输出「向左侧旋转约 165°」这种需要人脑换算的说法，改成了「近乎背对镜头」；
   - 抓出 `scripts/generate_xcodeproj.py` 里 `TARGETED_DEVICE_FAMILY` 少写引号、`mainGroup` 缺注释导致工具无法识别；
   - 抓出 `scripts/pick_simulator.py` 里按名称排序会让 `"iPhone SE (3rd generation)"` 排在 `"iPhone 15 Pro"` 之后，「取最后一台」实际挑到 SE —— 与注释语义不符；
   - 这一轮又补了三个**针对性**工具：
     - `scripts/openseplist.py` —— 按 OpenStep 文法**真正解析** `pbxproj`，报错带行列号与出错行原文（第 2 轮那个 `path = ;` 就是它精确定位到「第 204 行第 11 列」的）； 
     - `scripts/check_conformance.py` —— 检查 `Hashable` 能否合成、`init` 是否漏赋值（第 3、4 轮的两类错误）；
     - `scripts/validate_project.py` 的**孤儿对象检测** —— 它查出了 `Info.plist` 的 `PBXFileReference` 从未被任何 group 引用（生成器注释写着「给侧栏能点开看」，但实际没挂上去）。
   
   **这三个工具在信任之前都先拿「已知坏样本」验证过**。而且它们自己也有 3 个 bug 被修掉（孤儿检测曾经因为把定义行自身也算作「被引用」而永远返回空集；Hashable 检查跨进了嵌套类型造成假阳性；init 检查把 `T?` 可选属性误判为未初始化）—— 修完之后，它们现在报出的问题**零假阳性**。
2. **把编译 + 测试放进 CI 必过门槛**。`build` job 的 `needs: preflight`，且测试不过就不出 ipa。
3. **测试只写能用数字断言的逻辑**，不写「跑通即可」的测试 —— 所以第 5 轮那个浮点缺陷才能被 288 个断言里的 1 个抓住。**但也要清楚它的边界**：第 7 轮那个帧率缺陷，288 个断言一个都没碰到 —— 它算出了一个合法但无意义的数。这类问题只能靠「对着每个要显示的指标问一句：这个数在真实环境里会是多少」。

### 这个限制现在还剩什么后果

**编译期风险已经清零**（真的编过了、真的在 iOS 模拟器上跑过了）。剩下的是**运行期**风险：

- **真机上的实际延迟、耗电、发热**——模拟器测不出来；
- **采集卡的真实兼容性**——`UVCVideoInput` 依赖真机硬件，单元测试覆盖不到（见 [05 文档](05-单元测试说明.md)）；
- **iOS 版本差异**——部署目标是 iOS 17.0，但目前只在 18.5 SDK 的模拟器上跑过，没在 iOS 17 真机上验证。

## 一、需求中 6 项核心功能的完成度

### 功能 1：真实相机实时监看 ✅ 完成

**已实现**：

- 三路真实视频输入（UVC 直连 / 网络中继 / 内置摄像头），统一在 `VideoInputSource` 协议下，上层监看与分析**不需要知道自己接的是哪种输入**；
- **能力前置判定**：`VideoInputCapability` 在用户尝试之前就给出结论。iPhone 上选 UVC 会**立刻**说明系统限制并列出替代方案，不会让用户插上线等一个永远不来的设备；
- 画面显示、连接状态（未连接/连接中/监看中/不支持/异常）、输入设备信息（分辨率、帧率、像素格式，全部来自系统真实上报值）、全屏、缩放（1×–5×，持久化）、适配方式（完整适配/铺满）；
- 9 项参考线，全部可独立开关：三分线、九宫格、中心十字、中心垂直参考线、水平参考线、安全框（比例可调）、画面比例（原始/1:1/4:3/3:2/16:9/9:16）、人物包围框、画面长宽比遮罩；
- 实测帧率、帧龄、丢弃帧数（滚动窗口从真实帧时间戳计算，不是估算值）；
- 13 种明确错误码的失败状态，每种都有中文原因说明 + 可执行的解决建议；
- 断线检测（网络中继 10 秒无新帧自动断开连接，App 端弹出「视频流已停止约 N 秒」）+ 一键重新连接；
- iPad 上自动切换为 UVC 可用，首页能力卡片与输入面板的分支都跟着变。

### 功能 2：AI 姿势推荐 ✅ 完成

**已实现**：

- **32 条手工撰写的姿势**，覆盖全部 **12 类场景**（户外人像/城市街拍/咖啡馆人像/旅行写真/棚拍人像/情侣写真/半身/全身/坐姿/站姿/侧身/回头）与全部 **7 类风格**（自然松弛/高级时尚/温柔治愈/清冷电影感/复古胶片/阳光活力/极简高级）；
- 每条姿势包含需求列出的全部要素：身体旋转方向与角度、头部转向、下巴角度、视线落点（具体到「看向哪里」）、肩颈处理、靠近镜头的手、另一只手、重心分配、双腿姿态、环境互动方式、摄影师机位（含焦段建议）、构图建议、摄影师执行提示、难度等级、关键词；
- **离线本地 JSON 数据库**。打开页面即出结果，**户外没有信号也能用**。带版本号与加载失败提示（失败时会明确告诉你是文件缺失还是解析失败，不会静默显示空列表）；
- 离线推荐引擎：场景 5 分 / 风格 4 分 / 景别 3 分 / 场景偏好景别 2 分 / 难度超限每级 −3 分。**同分时按难度升序**（让新手优先拿到好执行的姿势），完全同分时按 id 排序（保证 UI 顺序稳定，不会每次刷新都跳动）；
- 每条推荐都给出「为什么推荐它」的理由（命中了哪些场景/风格/关键词）；
- 收藏、最近浏览记录（上限 20）、多条件筛选（场景多选 + 风格多选 + 景别 + 难度上限 + 关键词搜索）、三种浏览模式（智能推荐/我的收藏/全部）；
- 姿势详情页：分步动作分解（11 个环节）、俯视方向示意图、构图示意图、可复制到剪贴板（方便发给模特）。

**关键设计：姿势库存的是参数而不是文案**

JSON 里存的是 `bodyRotation: {degrees: 30, direction: left}` 这样的结构化参数，具体语句由 `PoseScriptWriter` 生成。**好处是角度数值和文字描述永远一致**，不可能出现「参数写 30°、文案写 45°」的矛盾。想改措辞改一个函数，想加姿势往 JSON 里加一条。

**没有做到 / 做不到的**：

| 事项 | 原因 |
|---|---|
| 姿势的**模特参考照片** | 无法生成真实照片，也不应该在 App 里塞入来源不明的图片。改为提供**俯视方向示意图 + 构图示意图**，并在详情页明确标注「本 App 不含模特示范实拍图」 |
| 云端 AI 生成为你量身定制的姿势 | 姿势推荐**完全离线**，所有姿势来自随 App 打包的本地数据库。（注：后来新增的「照片精修」是唯一会联网的功能，但它只做像素处理，不参与姿势推荐；见 [07 文档](07-照片精修管线.md)） |

### 功能 3：实时 AI 姿势指导 ✅ 完成（默认关闭）

**已实现**：

- Apple Vision `VNDetectHumanBodyPoseRequest`，19 个强类型关键点枚举；
- 骨架连线绘制（20 条边，按置信度降低不透明度和点尺寸）；
- 基于真实关键点坐标计算的指标**全部**：肩线倾斜、髋线倾斜、躯干左右倾斜、头部偏航（估算，含置信度）、头部歪斜、左右肘关节角度、手腕高度分带、人物中心偏移、画面边缘截断、肩到髋的躯干比例；
- 每条建议**都嵌入触发它的实测数值**（例如「实测：画面右侧肩膀比画面左侧低 10.0°」），方便你自己复核；
- **门控机制**：综合置信度 < 30% 或有效关键点 < 8 个时，只输出一条「关键点识别不稳定，暂不给角度结论」并列出识别不到的关节名。**不给近似值、不给猜测**；

- 阈值集中在一处（`PoseCoachEngine.Thresholds`）：肩线 3°/8°、躯干 4°、头部转角 15°、头部歪斜 6°、肘部 168°/55°、中心偏移 0.10/0.22；
- 按需开关，**默认关闭**（`livePoseEnabled = false`）以省电降热。

| 手指/手腕的精细朝向 | Vision 的人体姿态不提供手部关键点 |

### 功能 4：AI 构图分析 ✅ 完成

**已实现**：

- **头顶留白**（实测百分比，按 2% / 5% / 35% 三档给出不同级别与不同建议）；
- **视线方向留白**：根据头部偏航估算判断视线朝向，检查那一侧的留白是否够（阈值 6%）。**头部正对镜头时会明确说明「视线留白规则不适用」**，而不是硬套规则；
- **边缘截断**：检测人物包围框贴到哪一侧，并进一步检查**是否有某个关节正好压在画面边缘上**（这是裁切最容易出错的情况，会单独提示「建议改成切在小臂或大腿中段」）；
- **三分法**：计算人物中心与最近三分线的偏离度（容差 4.5%），并给出「需要横向移动约 X% 画面宽度」的可执行建议；
- **景别推断**：特写/半身/全身/坐姿，**并给出可核对的判断依据**（「人体包围框高度占画面 79%；膝与踝关键点均可见；膝关节角度小于 130°，判断为坐姿」）；
- **背景干扰**：通过人物区域外的边缘密度评估（阈值 0.42）。**实时模式下明确说明「本项不逐帧计算（会显著增加耗电），不给出结论」**，只在照片分析里给出真实数值 —— 不编造也不假装算过；
- **严格区分客观与主观**：每条结论文本前有「实测」或「建议」标签（`FindingKind.objective` / `.heuristic`），UI 上用不同颜色的徽章展示，摄影师可以自己决定采纳哪些；
- **置信度分档展示**：低（<35%）/ 中（35–70%）/ 高（≥70%），低置信度时自动显示「关键点识别不稳定，以下结论仅供参考」的提示条。

**没有做到 / 做不到的**：

| 事项 | 原因 |
|---|---|
| 没有人物时给出构图结论 | **刻意不做**。需求明确要求「如果没有摄像头连接，请提示用户连接，不要给出预设结果」。没有检测到人体时只输出一条「未检测到人物，无法做构图判断」 |
| 美学层面的「这张好不好看」 | 审美是主观的。本项目只给可测事实 + 有明确规则的摄影建议，并对两者做区分标注 |
| 实时的背景细节密度 | 逐帧计算背景边缘密度会显著增加耗电。实时模式不给结论，照片分析里给 |
| 精确的视线朝向（真 3D 注视方向） | 同功能 3，头部偏航是估算值 |

### 为什么要多加一个 G 页面

因为本项目有一个别人不会遇到的约束：**开发机是 Windows，没有 Mac**。而 `os.Logger` 的落盘内容只有 macOS 的「控制台」App 或 Xcode 才能读。也就是说，真机上一旦出问题，现场信息**在物理上就是取不出来的** —— 使用者只能在聊天里说「它不工作」。

G 页面就是把这个缺口补上：

- **看得见**：环境、权限、视频输入的真实连接参数、实测到达帧率、分析管线统计，全部直读自系统与当前会话；
- **拿得走**：日志同时进 `os_log` 与内存环形缓冲（400 条上限），可一键复制或导出成纯文本；
- **能定位**：中继探测会把「黑屏」拆成六种互不相同的结论 —— 连不上 / 超时 / HTTP 错误 / 能连上但没画面 / 正常 / 已取消，每种都给出可执行的下一步。这四种原因在界面上原本都只是「黑屏」。

**它不编造任何数值**：取不到就写「未知」，并说明是系统没提供。`iOS` 没有本地网络权限的查询接口，报告里就如实写「无法查询」，而不是写「已授权」。
