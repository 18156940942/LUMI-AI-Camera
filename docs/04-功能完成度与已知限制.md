### 为什么没有编译

开发这套代码的机器是 **Windows**，没有 Xcode，也没有 Swift 编译器。iOS App 只能在 macOS + Xcode 上编译，这是 Apple 工具链的硬限制，没有任何绕开的方式。

### 这个限制的实际后果

可能存在的、只有在编译时才会暴露的问题：

- **语法错误**（拼写、括号、泛型约束）——概率低但不可能为零；
- **API 签名不匹配**——例如某个系统方法的参数标签记错了；
- **类型推断失败**——SwiftUI 的 `ViewBuilder` 在复杂表达式里推断失败是常见坑；
- **`@ViewBuilder` 分支数超限**——一个 `body` 里超过 10 个顶层分支会报错；
- **`@Published` + `@MainActor` 的并发标注**在 Swift 6 严格模式下的告警（本项目用 Swift 5 语言模式规避）。

**运行期才可能发现的问题**：真机上的实际延迟、耗电、发热表现。

### 为了降低这个风险做了什么

1. **写了静态预检脚本**（`scripts/preflight.py`）。这个过程有实际收获——它抓出了：
   - 4 条姿势的身体旋转角度是 95°–165°，而我最初的校验阈值写的是 0–90°。数据其实是对的（背身回望确实要转 165°），错的是阈值。同时发现 `PoseRotation.descriptiveText` 在大角度下会输出「向左侧旋转约 165°」这种需要人脑换算的说法，改成了「近乎背对镜头」。
   - `scripts/generate_xcodeproj.py` 里 `TARGETED_DEVICE_FAMILY` 少写引号、`mainGroup` 缺注释导致工具无法识别。
   - `scripts/pick_simulator.py` 里按名称排序会让 `"iPhone SE (3rd generation)"` 排在 `"iPhone 15 Pro"` 之后，「取最后一台」实际挑到 SE —— 与注释语义不符。
2. **把编译 + 测试放进 CI 必过门槛**。第一次 `git push` 就会拿到真实的编译错误清单。
3. **测试只写能用数字断言的逻辑**，不写「跑通即可」的测试。

## 一、需求中 6 项核心功能的完成度

### 功能 1：真实相机实时监看 ✅ 完成

**已实现**：

- 三路真实视频输入（UVC 直连 / 网络中继 / 内置摄像头），统一在 `VideoInputSource` 协议下，上层监看与分析**不需要知道自己接的是哪种输入**；
- **能力前置判定**：`VideoInputCapability` 在用户尝试之前就给出结论。iPhone 上选 UVC 会**立刻**说明系统限制并列出替代方案，不会让用户插上线等一个永远不来的设备；
- 画面显示、连接状态（未连接/连接中/监看中/不支持/异常）、输入设备信息（分辨率、帧率、像素格式，全部来自系统真实上报值）、全屏、缩放（1×–5×，持久化）、适配方式（完整适配/铺满）；
- 9 项参考线，全部可独立开关：三分线、九宫格、中心十字、中心垂直参考线、水平参考线、安全框（比例可调）、画面比例（原始/1:1/4:3/3:2/16:9/9:16）、人物包围框、画面长宽比遮罩；
- 实测帧率、帧龄、丢弃帧数（滚动窗口从真实帧时间戳计算，不是估算值）；
- 13 种明确错误码的失败状态，每种都有中文原因说明 + 可执行的解决建议；
- 断线检测（网络中继 10 秒无新帧自动断开连接，App 端弹出「视频流已停止约 N 秒」）+ 一键重新连接；
- iPad 上自动切换为 UVC 可用，首页能力卡片与输入面板的分支都跟着变。

**没有做到 / 做不到的**：

| 事项 | 原因 |
|---|---|
| iPhone 上 UVC 采集卡直连 | **系统层面不可能**。Apple DTS 官方确认 iPhone 不支持外接摄像头，`AVCaptureDevice.DeviceType.external` 在 iPhone 上 DiscoverySession 永远返回空。详见 [01 文档](01-技术可行性与风险.md) |
| 相机机身曝光参数（光圈/快门/ISO） | HDMI 采集卡只传视频像素，不传相机的曝光元数据。这是 HDMI 协议的范畴，不是软件能补的 |
| 监看画面录制/回放 | 需求里没有要求，未实现 |

### 功能 2：AI 姿势推荐 ✅ 完成

**已实现**：

- **32 条手工撰写的姿势**，覆盖全部 **12 类场景**（户外人像/城市街拍/咖啡馆人像/旅行写真/棚拍人像/情侣写真/半身/全身/坐姿/站姿/侧身/回头）与全部 **7 类风格**（自然松弛/高级时尚/温柔治愈/清冷电影感/复古胶片/阳光活力/极简高级）；
- 每条姿势包含需求列出的全部要素：身体旋转方向与角度、头部转向、下巴角度、视线落点（具体到「看向哪里」）、肩颈处理、靠近镜头的手、另一只手、重心分配、双腿姿态、环境互动方式、摄影师机位（含焦段建议）、构图建议、摄影师执行提示、难度等级、关键词；
- **离线本地 JSON 数据库**。打开页面即出结果，**户外没有信号也能用**。带版本号与加载失败提示（失败时会明确告诉你是文件缺失还是解析失败，不会静默显示空列表）；
- 离线推荐引擎：场景 5 分 / 风格 4 分 / 景别 3 分 / 场景偏好景别 2 分 / 难度超限每级 −3 分。**同分时按难度升序**（让新手优先拿到好执行的姿势），完全同分时按 id 排序（保证 UI 顺序稳定，不会每次刷新都跳动）；
- 每条推荐都给出「为什么推荐它」的理由（命中了哪些场景/风格/关键词）；
- 收藏、最近浏览记录（上限 20）、多条件筛选（场景多选 + 风格多选 + 景别 + 难度上限 + 关键词搜索）、三种浏览模式（智能推荐/我的收藏/全部）；
- 姿势详情页：分步动作分解（11 个环节）、俯视方向示意图、构图示意图、可复制到剪贴板（方便发给模特）。

**关键设计：姿势库存的是参数而不是文案**

JSON 里存的是 `bodyRotation: {degrees: 30, direction: left}` 这样的结构化参数，具体语句由 `PoseScriptWriter` 生成。**好处是角度数值和文字描述永远一致**，不可能出现「参数写 30°、文案写 45°」的矛盾。想改措辞改一个函数，想加姿势往 JSON 里加一条。

**没有做到 / 做不到的**：

| 事项 | 原因 |
|---|---|
| 姿势的**模特参考照片** | 无法生成真实照片，也不应该在 App 里塞入来源不明的图片。改为提供**俯视方向示意图 + 构图示意图**，并在详情页明确标注「本 App 不含模特示范实拍图」 |
| 云端 AI 生成为你量身定制的姿势 | 本项目**刻意不引入任何云端调用**（这也是「没有 API 密钥可泄漏」的原因）。所有姿势来自本地数据库 |

### 功能 3：实时 AI 姿势指导 ✅ 完成（默认关闭）

**已实现**：

- Apple Vision `VNDetectHumanBodyPoseRequest`，19 个强类型关键点枚举；
- 骨架连线绘制（20 条边，按置信度降低不透明度和点尺寸）；
- 基于真实关键点坐标计算的指标**全部**：肩线倾斜、髋线倾斜、躯干左右倾斜、头部偏航（估算，含置信度）、头部歪斜、左右肘关节角度、手腕高度分带、人物中心偏移、画面边缘截断、肩到髋的躯干比例；
- 每条建议**都嵌入触发它的实测数值**（例如「实测：画面右侧肩膀比画面左侧低 10.0°」），方便你自己复核；
- **门控机制**：综合置信度 < 30% 或有效关键点 < 8 个时，只输出一条「关键点识别不稳定，暂不给角度结论」并列出识别不到的关节名。**不给近似值、不给猜测**；
- 左手/右手、左肩/右肩的描述统一按**画面左右**排序，不依赖 Vision 的 left/right 命名（两者在正面人像里是相反的，直接用会导致左右说反）；
- 阈值集中在一处（`PoseCoachEngine.Thresholds`）：肩线 3°/8°、躯干 4°、头部转角 15°、头部歪斜 6°、肘部 168°/55°、中心偏移 0.10/0.22；
- 按需开关，**默认关闭**（`livePoseEnabled = false`）以省电降热。

**没有做到 / 做不到的**：

| 事项 | 原因 |
|---|---|
| 真正意义上的 3D 姿态解算 | 用的是单目 2D 关键点。头部偏航只能通过「鼻尖相对双耳中点的偏移」估算，UI 上一律标注「估算」且置信度打 0.8 折 |
| 与参考姿势的自动比对（「你应该再转 10°」） | 需要把实时检测结果与姿势库的期望参数对齐，涉及视角归一化等问题。**未实现**，需求里也没有明确要求 |
| 多人场景的姿势指导 | 当前取第一个检测到的人。情侣姿势的双人指导**未实现**（姿势库里有意设计了 3 条情侣姿势，但实时指导只针对单人） |
| 手指/手腕的精细朝向 | Vision 的人体姿态不提供手部关键点 |

### 功能 4：AI 构图分析 ✅ 完成

**已实现**：

- **头顶留白**（实测百分比，按 2% / 5% / 35% 三档给出不同级别与不同建议）；
- **视线方向留白**：根据头部偏航估算判断视线朝向，检查那一侧的留白是否够（阈值 6%）。**头部正对镜头时会明确说明「视线留白规则不适用」**，而不是硬套规则；
- **边缘截断**：检测人物包围框贴到哪一侧，并进一步检查**是否有某个关节正好压在画面边缘上**（这是裁切最容易出错的情况，会单独提示「建议改成切在小臂或大腿中段」）；
- **三分法**：计算人物中心与最近三分线的偏离度（容差 4.5%），并给出「需要横向移动约 X% 画面宽度」的可执行建议；
- **景别推断**：特写/半身/全身/坐姿，**并给出可核对的判断依据**（「人体包围框高度占画面 79%；膝与踝关键点均可见；膝关节角度小于 130°，判断为坐姿」）；
- **背景干扰**：通过人物区域外的边缘密度评估（阈值 0.42）。**实时模式下明确说明「本项不逐帧计算（会显著增加耗电），不给出结论」**，只在照片分析里给出真实数值 —— 不编造也不假装算过；
- **严格区分客观与主观**：每条结论文本前有「实测」或「建议」标签（`FindingKind.objective` / `.heuristic`），UI 上用不同颜色的徽章展示，摄影师可以自己决定采纳哪些；
- **置信度分档展示**：低（<35%）/ 中（35–70%）/ 高（≥70%），低置信度时自动显示「关键点识别不稳定，以下结论仅供参考」的提示条。

**没有做到 / 做不到的**：

| 事项 | 原因 |
|---|---|
| 没有人物时给出构图结论 | **刻意不做**。需求明确要求「如果没有摄像头连接，请提示用户连接，不要给出预设结果」。没有检测到人体时只输出一条「未检测到人物，无法做构图判断」 |
| 美学层面的「这张好不好看」 | 审美是主观的。本项目只给可测事实 + 有明确规则的摄影建议，并对两者做区分标注 |
| 实时的背景细节密度 | 逐帧计算背景边缘密度会显著增加耗电。实时模式不给结论，照片分析里给 |
| 精确的视线朝向（真 3D 注视方向） | 同功能 3，头部偏航是估算值 |

### 功能 5：照片导入与 AI 筛选 ✅ 完成

**已实现**：

- 系统照片选择器（`PhotosPicker`），一次最多选 30 张，**只读取你主动挑选的照片**；
- 把一份**副本**存入 App 沙盒（`LUMIPhotos/`），所有分析与操作都只作用于副本；
- 预览（ImageIO 缩略图，按需降采样，不把原图整个读进内存）、基本信息展示；
- **真实 EXIF 读取**：机身、镜头、焦距（含等效焦距）、光圈、快门、ISO、尺寸、拍摄时间。**读不到就是 `nil`，UI 显示「未提供」，绝不填默认值**；
- **画质客观指标**：清晰度（拉普拉斯方差归一化）、平均亮度、对比度、过曝/欠曝像素比例、整体与背景边缘密度；
- **闭眼检测**：Vision 人脸特征点的眼部开合比例（上下眼睑距离 / 眼角宽度，阈值 0.17）。**明确标注为启发式判断**，建议文案里要求「放大确认后再决定是否剔除」；
- **姿态评估**：完整的 `PoseAnalyzer` + `PoseCoachEngine` 链路（与实时指导共用同一套逻辑）；
- **构图评估**：`CompositionAnalyzer` + 背景干扰数值（这里会真实计算，与实时模式不同）；
- **综合筛选建议**：清晰度、曝光、闭眼、姿态、构图各自扣分后得出 0–100 的综合分，并给出顶层结论（建议保留 / 建议人工复核 / 可考虑剔除）；
- 收藏、场景标签（手动选择，明确说明「不会为此填充任何推测值」）、按日期分组、按场景分组、收藏夹视图、待复核视图；
- 应用内删除（**删除前确认框里明确写着「相册中的原始照片不会被删除」**）；
- 照片页顶部有 5 条**数据边界说明**，明确告知 App 的能力边界。

**没有做到 / 做不到的**（这一项的限制最多，也最需要在 UI 上说明清楚）：

| 事项 | 原因 | UI 上怎么说的 |
|---|---|---|
| 读取相机存储卡 | iOS 沙盒不允许 App 访问相机的可移动存储。相机插到 iPhone 上走的是 PTP 协议，第三方 App 无法读取其中的照片 | 照片页的边界说明里明确写了，并给出三种正常路径：SnapBridge 传到手机相册 → 用 LUMI 导入；或用读卡器导入相册后再导入 |
| 读取尚未传输到 iPhone 的照片 | 同上。App 只能看到 iOS 相册或自己沙盒里的内容 | 同上 |
| 真正的闭眼分类器 | 用的是特征点几何比例启发式，不是训练过的模型。会误判（尤其是低分辨率、大角度侧脸、戴眼镜时） | 每处都标注「启发式」，建议文案要求人工确认 |
| 自动删除相册原图 | **刻意不做**。App 完全没有调用任何 PhotoKit 的删除 API | 明确说明「永远不会删除或修改你的原始照片」 |
| 自动修图（去噪、调色、人像美化） | 需求里没有要求；这是另一个产品方向 | — |
| 人脸识别/分组 | 需要额外权限与模型，需求里没有要求 | — |

## 五、逐阶段报告（需求里的 8 个阶段）

### 阶段 1：分析 Z6 II ↔ iPhone 15 Pro 视频输入可行性 ✅

**做了什么**：查阅 Apple 开发者文档、WWDC 2023 场次与 Apple DTS 工程师在开发者论坛的答复，确认 iPhone 15 Pro 不支持 UVC 外接摄像头。核对 Z6 II 的 HDMI 输出规格与限制条件。设计三条真实可行的监看路径。

**测试了什么**：结论有明确出处可核对（见 01 文档引用的原话）。

**限制**：无法在真机上实测各路径的实际延迟（需要 iPhone + 采集卡 + Z6 II 齐备）。

→ 产出：[`docs/01-技术可行性与风险.md`](01-技术可行性与风险.md)

### 阶段 2：搭建完整原生 iOS 项目 ✅

**做了什么**：51 个 Swift 文件的完整项目，按 App / Models / VideoInput / PoseEstimation / AIAnalysis / PhotoLibrary / Services / ViewModels / Views / Resources 分层。6 个页面全部实现，含设置持久化、日志、横屏锁定、深色主题。

**测试了什么**：工程文件结构校验（UUID 引用完整性、Sources/Resources 覆盖度、必需配置项）通过。

**限制**：未编译。

### 阶段 3：姿势推荐数据库与收藏 ✅

**做了什么**：32 条手工撰写的姿势，覆盖全部 12 场景 / 7 风格。结构化参数 + 文案生成器的双层设计。离线推荐引擎（显式可测的权重表）。收藏、最近浏览、多条件筛选、搜索。

**测试了什么**：JSON 与 Swift 枚举的交叉校验（全部 32 条的每个枚举字段）、id 唯一性、场景/风格全覆盖、难度与构图比例区间、旋转方向与角度自洽性。**这个过程抓出了 4 条姿势的角度阈值问题与 1 处文案缺陷。**

### 阶段 4：真实人体姿态检测与本地姿势指导 ✅

**做了什么**：Vision 封装（含置信度综合算法）、19 个关键点的强类型枚举、纯函数几何工具、`PoseAnalyzer`、带门控的 `PoseCoachEngine`、按置信度绘制的骨架视图。

**测试了什么**：几何方向约定（含 Vision 原点左下 vs SwiftUI 原点左上的陷阱）、各角度计算的手算期望值、**门控行为**（低置信度必须只输出一条且不含任何角度结论）、阈值边界（3°/8°、4°、15°、6° 的临界值）。

**限制**：头部偏航是估算（单目 2D 关键点的固有限制），已在 UI 上标注。

### 阶段 5：接入真实视频输入 ✅

**做了什么**：三路输入的统一协议 + 三个适配器。UVC（AVCaptureSession + `.external` DiscoverySession，iPhone 上主动抛错）、网络中继（自写的 multipart JPEG 解析器 + 帧节流 + 停顿检测 + 真实带宽统计；HLS 走 AVPlayer + AVPlayerItemVideoOutput + CADisplayLink）、内置摄像头（含权限申请与旋转协调）。零拷贝预览层。13 种错误码。

**测试了什么**：能力判定的正确性（`supportsExternalCamera` 与实际 idiom 一致、UVC 在 iPhone 上必须返回 false）、RelayConfiguration 的 URL 拼装（含斜杠归一化、host 去空格）、Codable 往返。

**限制**：iPhone 上 UVC 不可用（系统限制）；实际延迟未实测。

### 阶段 6：视频构图分析 ✅

**做了什么**：`CompositionAnalyzer`（8 项检查，每项都区分实测/建议）、`ImageQualityCalculator`（灰度降采样 + 拉普拉斯方差 + 边缘密度）、`FrameAnalysisPipeline`（帧率节流 + 串行 Vision 队列 + 诊断信息）。

**测试了什么**：阈值边界（头顶留白 0.5%/3.5%/10.4%/37%）、**无人物门控**（必须只有一条结论且所有测量量为空）、三分线容差、景别推断的四种分支、背景干扰「没算就说没算」、纯色图的方差必须为 0、棋盘格必须高、归一化必须钳制在 0…1。

### 阶段 7：照片导入与筛选 ✅

**做了什么**：照片选择器接入、沙盒副本管理（`index.json`）、ImageIO 缩略图、EXIF 读取器（只读真实字段）、`PhotoAnalyzer`（像素 + Vision 人脸 + 姿态 + 构图）、综合评分与筛选结论、四种分组视图、删除确认。

**测试了什么**：真实 JPEG 的 EXIF 往返（写入→读出，含日期格式解析）、**缺字段必须为 nil 而不是填默认值**、格式化函数（光圈/快门/焦距/等效焦距/像素）、`verdict` 的四条分支、非图像数据必须返回 nil。

**限制**：无法读取相机存储卡（iOS 沙盒限制，UI 上已说明）；闭眼检测是启发式（已标注）。

### 阶段 8：编译、测试、修复错误、完善文档 ⚠️ 部分完成

**做了什么**：预检脚本（3 个）、Xcode 工程生成器、云端构建流水线（含单元测试门槛与 ipa 结构校验）、中继脚本、5 份文档。

**测试了什么**：预检 7 项全绿、工程结构校验通过、工作流 YAML 结构校验通过、中继脚本 AST 与状态页模板校验通过、模拟器选择逻辑的单元测试。

**限制**：**编译与单元测试执行未完成**（无 macOS 环境）。这是本项目唯一一个明确不完整的阶段，也是为什么它在文档里被反复标注。

## 六、下一位维护者（或者未来的我）最该先做的事

按优先级：

1. **推送到 GitHub，看 CI 的编译结果**。大概率会有几处需要修（SwiftUI 的 `ViewBuilder` 类型推断、`@MainActor` 标注、某个 API 的参数标签）。这是投入产出比最高的一步。
2. **让单元测试真正跑起来**。测试逻辑是按手算期望值写的，但没执行过。跑起来之后如果有失败，**先怀疑测试写错而不是源码写错** —— 尤其是几何类的断言（我在写的时候就修正过几次自己的手算）。
3. **接上硬件实测延迟**。这是唯一无法靠静态分析获得的指标，直接决定这个工具在拍摄现场好不好用。
4. **实测耗电与发热**。特别是同时开实时姿势指导 + 构图分析的场景。阈值（分析帧率默认 8 fps、分析分辨率上限 720px）是我按经验设的，可能需要按实测调整。
5. **考虑把「姿势参数 ↔ 实时检测结果」做对齐**。这是让姿势助手从「查手册」进化到「实时纠错」的关键一步，也是当前最明显的功能空白。
